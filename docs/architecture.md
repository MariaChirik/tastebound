# Архітектура

Система складається з мікросервісів: API Gateway (Nginx), Auth, Catalog, Order, Payment,
Tracking, Notification (API і фоновий обробник черги), Recommendation і Frontend.
Користувачі, ресторани, страви, замовлення і спільні кошики зберігаються в PostgreSQL.
Платежі, маршрути й позиції кур'єрів, черга та історія сповіщень і оцінки страв - у Redis.
Листи локально приймає тестова поштова скринька Mailpit.

Кожен сервіс сам перевіряє токен входу, підписаний спільним ключем `AUTH_SECRET_KEY`.
Order передає токен користувача далі в Payment і Tracking, тому кожен сервіс знає, хто
виконує дію.

| Сервіс | Ендпоїнти |
| --- | --- |
| Auth | `POST /register`, `POST /login`, `GET /users`, `POST /users/<email>/status` (адміністратор) |
| Catalog | `GET /dishes` (фільтри `exclude_allergens`, `diet`, `ids`), `GET /restaurants`, `GET/POST /menu`, `PATCH /menu/<id>`, `POST /menu/overload`, `GET /admin/dishes`, `POST /admin/dishes/<id>/hidden` |
| Order | `POST /orders`, `GET /orders`, `GET /orders/<id>`, `POST /orders/<id>/pay`, `POST /orders/<id>/pay/check`, `POST /orders/<id>/cancel`, `POST /orders/<id>/advance`, `POST /groups`, `GET /groups/<code>`, `PUT /groups/<code>/items`, `POST /groups/<code>/checkout` |
| Payment | `POST /pay`, `GET /payments/<order_id>`, `POST /payments/<order_id>/check`, `POST /payments/<order_id>/cash`, `POST /refund/<order_id>`, `POST /liqpay/callback` |
| Tracking | `POST/GET /orders/<id>/status`, `POST/GET /orders/<id>/location` |
| Notification | `GET /users/<user>`, `POST /notifications`, `POST /notifications/process`, `GET /notifications/pending` |
| Recommendation | `POST /ratings`, `GET /ratings/<user>`, `GET /recommendations/<user>` |

У кожного сервісу також є `GET /health`.

## Ролі

- **Клієнт** вказує алергени в профілі, оформлює звичайне або спільне замовлення, платить
  свою частку, бачить кур'єра на мапі й оцінює страви.
- **Співробітник ресторану** веде меню (склад, алергени, дієти), вмикає й вимикає страви
  в стоп-листі, вмикає режим перевантаження і готує замовлення.
- **Кур'єр** бачить замовлення в дорозі, ділиться геопозицією, отримує готівку
  і позначає доставку.
- **Адміністратор** створюється з `.env`, підтверджує співробітників і кур'єрів,
  блокує користувачів і приховує страви.

## Життєвий цикл замовлення

1. Клієнт обирає страви одного ресторану, адресу на мапі й, за бажанням, час доставки.
   Order бере ціни й наявність із Catalog і рахує відстань до ресторану за координатами.
2. Час доставки: приготування (15 хв + 2 хв за кожну додаткову порцію), черга кухні
   (4 хв за кожне активне замовлення ресторану), передача кур'єру (5 хв) і дорога
   (20 км/год). Заплановане замовлення має бути не раніше цього часу і не пізніше 7 днів.
3. Замовлення чекає, поки кожен учасник оплатить свою частку карткою (LiqPay sandbox або
   локальний тестовий режим) чи обере готівку. Лише після цього його бачить ресторан.
4. Ресторан переводить замовлення в «Готується», потім «У дорозі». Order передає
   в Tracking маршрут, і клієнт бачить кур'єра на мапі: за геопозицією з його телефону
   або за розрахунком часу в дорозі.
5. Кур'єр позначає «Доставлено», готівкові частки стають оплаченими.
6. До початку приготування замовлення можна скасувати, оплачені частки повертаються
   автоматично.
7. На кожну подію Order і Payment кладуть повідомлення в чергу Redis. Обробник
   Notification надсилає лист і зберігає історію (останні 20) для розділу «Сповіщення».

## Спільне замовлення

Клієнт створює групу й отримує посилання. Колеги відкривають посилання, входять і додають
свої страви з того самого ресторану. Організатор вказує адресу й оформлює замовлення,
після чого кожен учасник оплачує свою частку окремо.

## Рекомендації

Recommendation бере каталог із Catalog (з урахуванням алергенів користувача) і пропонує
страви, яких користувач ще не оцінював. Бали: +2 за той самий ресторан, що й страви з
оцінкою 4-5, +1 за кожну спільну дієту, плюс середня оцінка інших користувачів.
Біля кожної рекомендації показується причина.

## Середовища та інфраструктура

- **Розробка і CI** - Docker Compose: сервіси в мережі backend, фронтенд і шлюз у мережі frontend,
  дані PostgreSQL і Redis у томах. У CI застосунок піднімається з паролями з GitHub Secrets
  і перевіряється через шлюз.
- **Образи** - після злиття в main CI публікує образи всіх сервісів у GitHub Container Registry
  (`ghcr.io/mariachirik/tastebound-<сервіс>`) з тегами `latest` і коротким хешем коміту.
- **Сервер** - Terraform (`infra/`) описує в AWS мережу VPC, брандмауер, віртуальну машину з k3s,
  диск для даних і статичну IP-адресу.
- **Kubernetes** - маніфести в `deploy/k8s/`: PostgreSQL і Redis як StatefulSet з постійними томами,
  сервіси як Deployment з перевірками readiness і liveness та оновленням без зупинки,
  налаштування в ConfigMap, паролі в Secret, зовнішній доступ через Ingress.

## Тестування

- **Unit-тести** (PyTest і Node test runner) запускаються для кожного сервісу окремо. CI вимагає
  покриття коду щонайменше 85% і зберігає звіти JUnit і покриття як артефакти.
- **API-тести** - колекція Postman у `tests/postman/`. CI піднімає застосунок через Docker Compose
  і запускає колекцію через Newman, звіт зберігається як артефакт.
- Публікація образів у реєстр запускається лише після успішних unit- і API-тестів.
